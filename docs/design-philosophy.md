# MergeCraft 设计思想

## 目标

MergeCraft 用 Plugin 分发团队知识和工作流，解决规范反复解释、经验难以
复用以及关键流程容易遗漏的问题。它不重复封装模型已经具备的通用能力。

设计一项能力时，先回答：

> 不做这项封装，团队会反复付出什么成本？

如果答案只是少输入几条普通命令，就不值得封装。

## 四层职责

| 层次 | 职责 | 示例 |
|------|------|------|
| LLM 原生能力 | 通用推理和常规操作 | 编码、Git、分析 diff、解决普通冲突 |
| Skills | 团队知识和需要上下文的软性判断 | 分支规范、Review 清单、故障排查路径 |
| Commands | 有独立价值的显式工作流入口 | commit + push + 创建 GitLab MR |
| Scripts / Hooks / CI | 确定执行和强制门禁 | format、测试、密钥扫描、发布检查 |

Plugin 是以上能力的组织和分发容器，不应与 Command 画等号。

## 什么时候创建 Skill

Skill 应至少满足以下条件中的两项：

- 多名成员反复使用。
- 每次都要补充相同的团队背景。
- 团队约定不同于通用实践。
- 存在固定但需要上下文判断的分析路径。
- 真实任务中反复出现遗漏或误判。
- 错误执行会产生明显的 Review 或返工成本。

Skill 应描述团队特有的选择和边界，不教授模型通用知识。例如，应记录
“MR 默认指向 dev 并 squash”，而不是逐步解释如何执行 `git push`。

## 什么时候创建 Command

Command 适用于用户需要明确触发，且本身形成完整结果的工作流：

- 组合多个系统，例如 Git、GitLab 和包管理平台。
- 参数和结果边界明确。
- 中途失败需要规定停止或恢复策略。
- 用户希望用统一入口表达完整意图。

普通的 branch、commit、push、代码总结等能力直接交给 LLM。只有包装普通
CLI、没有团队决策的 Command 应删除。

## 什么时候使用 Agent

Agent 只用于被多个 Command 或 Skill 复用的专业任务，且独立上下文能明显
降低复杂度。单个 Command 专用的命名、总结或格式生成不创建 Agent，避免
额外上下文和委派成本。

## 什么时候使用确定性工具

Skill 只能提高遵循规范的概率，不能构成强制保证。以下要求应交给程序：

- 格式化和 lint。
- 测试、类型检查和构建。
- 密钥与依赖漏洞扫描。
- 发布前置条件。
- 禁止合并或部署的质量门禁。

LLM 负责选择工具、组织流程、解释结果和处理非确定性判断；工具负责可靠执行。

## Skill 设计要求

每个 Skill 都应明确：

- 何时触发以及何时不触发。
- 需要哪些团队或项目上下文。
- 必须遵循的规则和默认值。
- 哪些操作需要确认。
- 失败后允许修复到什么程度。
- 如何验证结果。

按全团队、技术栈和具体项目划分知识，避免创建包罗万象的大 Skill。

## 演进方式

先让 LLM 在真实任务中直接执行，记录重复提示、Review 反馈和失败案例。只有
问题反复出现时才提炼 Skill 或确定性工具，并通过以下指标验证收益：

- 重复 Review 意见是否减少。
- 人工补充提示的次数是否下降。
- 首次任务通过率是否提高。
- Skill 是否误触发或漏触发。
- 流程是否增加了不必要的步骤。

规则必须有负责人和事实来源，并定期删除已经过时或被模型、工具原生覆盖的内容。

## 当前选择

普通 Git 的操作机制使用模型原生能力；`skills/git-workflow/SKILL.md` 为写
操作补充团队约定和安全边界。Claude Code 保留两个显式交付入口：
`/commit-push` 负责 commit、pre-commit 失败处理和 push 的完整边界，
`/commit-push-mr` 在此基础上继续创建 GitLab MR。前者的价值是统一 hook
失败后的停止与恢复策略，不是重复包装 Git 命令。

规则演进遵循“真实失败证据 → 重复摩擦 → 规则与例外 → 场景评测 → 发布门禁”。
评测同时记录正确性、耗时、Token、工具调用和远程往返。未通过阻断项检查、
超过性能预算或相对 baseline 没有收益时，不发布新规则。
